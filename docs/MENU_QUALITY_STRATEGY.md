# メニュー質的深化の方針：4案の評価と推奨

## 目指すゴール

現状の「本数×距離m（EN1/EN2/EN3）」から、次のレベルへ：

1. **セット構成**：ディセンディング、1-4 Dec、Build、Negative split 等
2. **ドリル・セットの具体的内容**：
   - (a) 奇数本：ヘッドアップ / 偶数本：キャッチアップ
   - (b) 1本目 H-E / 2本目 E-H / 3本目 E / 4本目 H（25m×4本の例）
   - (c) odd: Drill / even: Swim、odd: Pull / even: Kick 等

---

## 4案の評価

### 案1: 高城コーチのメニューを何百個もインプット

| 観点 | 評価 |
|------|------|
| **長所** | 本物の表現・構成が得られる。RTスタイルの一貫性が高い |
| **短所** | 収集・整形の工数が大きい。過去メニューへの過適合リスク。新条件への対応はモデル任せ |
| **実装** | 数百件を context に入れると token 制限に。RAG 等で検索して関連のみ渡す方式なら可能 |

**結論**: 中核にはしづらいが、**「質の高いサンプル集」として 20〜50 件**を選んで辞書化する価値は大きい。

---

### 案2: 代表サンプル数本 + 私が生成ロジックを構築

| 観点 | 評価 |
|------|------|
| **長所** | 工数が小さい。パターンが明確なら再現性が高い |
| **短所** | 「ロジック」で扱うのは **パターンの組み合わせ**まで。創造的な一文はモデルに任せる必要がある |
| **実装** | パターン辞書（odd/even、1H/1E、Des、1-4 Dec 等）を定義し、モデルに「これらから選んで組み合わせろ」と指示する形になる |

**結論**: 実装の主軸として **最も現実的**。パターンを「語彙」として定義し、モデルに選択・組み合わせをさせる。

---

### 案3: コーチの思想 + APIでネット検索

| 観点 | 評価 |
|------|------|
| **長所** | 最新情報・多様なネタを拾える |
| **短所** | 用語・品質がバラバラ。RT/高城コーチのトーンから外れやすい。「ディセンディング」などの言い回しもサイトごとに違う |
| **実装** | 既に SERPER 検索あり。補助的な参照として使う分には有効 |

**結論**: メインの設計思想にはしない。**補助的な情報源**として、信頼できるソースに限定するならあり。

---

### 案4: 完全オリジナル（モデル任せ）

| 観点 | 評価 |
|------|------|
| **長所** | データ準備が不要 |
| **短所** | 現状がまさにこれに近く、「質が薄い」と感じられている。ガイドがないと汎用的になりがち |

**結論**: このまま単体で使うのは避けたい。**他案と組み合わせる前提**で考える。

---

## 推奨：ハイブリッド（案2 主体 + 案1 軽量 + 案3 補助）

### 構造のイメージ

```
┌─────────────────────────────────────────────────────────┐
│ 1. コーチ思想（既存）                                      │
│    トーン・安全・期の制御を決める                           │
├─────────────────────────────────────────────────────────┤
│ 2. パターン辞書（新規・拡充）                               │
│    - セット構成: Des, 1-4 Dec, Build, Negative split...   │
│    - ドリル変形: odd/even, 1H/1E Alt, 本数別指示...       │
│    → モデルは「ここから選んで組み合わせる」                 │
├─────────────────────────────────────────────────────────┤
│ 3. 高品質サンプル（案1 軽量）                               │
│    10〜30件の「こういう書き方」を示す例                     │
│    → menu-dictionary または few-shot として                │
├─────────────────────────────────────────────────────────┤
│ 4. ネット検索（案3・オプション）                            │
│    補足情報のみ。メイン設計には使わない                     │
└─────────────────────────────────────────────────────────┘
```

### なぜこの組み合わせか

1. **案2 を主軸にする理由**
   - 「奇数はヘッドアップ、偶数はキャッチアップ」のような形は、**パターン（型）として定義できる**
   - 型を列挙しておけば、モデルは「どれをどのブロックで使うか」を選ぶだけでよい
   - 既存の menu-dictionary を、**セット構成・変形パターン**まで拡張するだけで進められる

2. **案1 を軽く使う理由**
   - 「数本」ではなく「数十本」あると、表現の幅と文体の参考になる
   - 全部を毎回渡す必要はなく、**良い例として 3〜5 件を few-shot に含める**程度で十分

3. **案3 を補助に抑える理由**
   - メインの品質は「思想＋パターン辞書＋サンプル」で担保する
   - ネットは「新しいドリル名を探す」くらいの使い方にとどめる

## 実装ステップ（案）

### Phase 1: パターン辞書の拡充（即時対応可能）

`menu-dictionary.md` または新規 `content/common/menu-patterns.md` に以下を追加：

```markdown
## セット構成パターン（必ず1つ以上を使用）

| パターン | 意味 | 記述例 | 主な用途 |
|----------|------|--------|----------|
| Des / 1-4 Dec | 本数ごとにタイムを落とす | Kick 4×50m（Des）（EN1）| Kick, Main |
| 1H/1E Alt | 1本目Hard・2本目Easy 交互 | Main 8×50m（EN3）｜1H/1E Alt | Main |
| 1-4 Dec, 5 Hard Alt | 1-4本Dec、5本目Hard | Kick 10×50m｜1-4 Dec, 5 Hard Alt | Kick |
| odd: X / even: Y | 奇数本X、偶数本Y | Drill odd: ヘッドアップ / even: キャッチアップ 8×50m | Drill |
| Build | 本数ごとに徐々に上げる | Cho 100m Build（EN1）| W-up |
| Negative split | 後半を速く | Pull 4×100m Negative split（EN2）| Pull, Main |

## ドリル変形パターン

- odd: ヘッドアップ / even: キャッチアップ
- odd: Drill / even: Swim
- odd: Pull / even: Kick
- 1本目 H-E / 2本目 E-H / 3本目 E / 4本目 H（25m×4本など）
- 50m Drill / 50m Swim（100m単位）
- 1kick / 2pull（25mキック＋50mプル）
```

プロンプトでは「上記パターンから必ず選び、内容欄に明記する」と指示。

### Phase 2: サンプル参照の追加

- 高城コーチ等のメニューから、質の高い 5〜10 件を選ぶ
- 各ブロックの「理想的な書き方」を 1〜2 文ずつ抽出
- システムプロンプトまたは commonContent に「出力スタイルの参照例」として含める

### Phase 3: プロンプトの強化

- 「EN1/EN2 だけの汎用表現は禁止。必ずセット構成またはドリル変形パターンを1つ以上含める」
- 出力形式の例に、上記パターンを用いた具体例を追加

---

## 方針が固まっていないことについて

「どの案か」で迷うより、**役割分担**で考えると整理しやすいです：

- **思想・制御** → コーチの思想（既存でOK）
- **語彙・型** → パターン辞書（案2）
- **文体・粒度** → 少数のサンプル（案1 軽量）
- **新規ネタ** → ネット検索（案3・オプション）

まずは **Phase 1（パターン辞書の拡充）** から着手し、生成結果を見ながら Phase 2 でサンプルを足していく進め方が、コストと効果のバランスが良いと思います。
