# 練習メニュー サンプル要件・完成図

高城コーチのメニューと SSAI（APIモデル）を掛け合わせて品質を無限大に広げるための、具体的な要件定義と進め方。

---

## 前提：APIが「読み取れる」ことの限界と可能性

### 限界
- APIモデルは**学習しない**。毎回プロンプト（指示文＋参照データ）で「条件づけ」されるだけ。
- **思考パターン**を直接読み取ることはできない。テキストとメタデータから**推論**するのみ。
- 強化選手向け・障害者向けなど**意図の違い**は、**メタデータ（条件・作成意図）を明示**しないと区別できない。
- EN1/EN2、ムーブメント要素、作成意図が混在する**完全な構造化**は現実的に難しい。

### 可能性
- **条件＋本文＋意図**をセットで渡せば、「今回の条件に近いサンプルはこれ。この意図で作られている。同じスタイルで生成せよ」と**条件づけ**できる。
- 意図を**短い注釈**として付ければ、モデルはそれを手がかりに文体・粒度を合わせる。
- パターン（odd/even、Des、1H/1E Alt）を**辞書化**すれば、モデルは「語彙」として使い回せる。

→ **完全構造化は目指さず、「条件・本文・意図」の3点セットで渡す**方針が現実的。

## 1. 練習メニューの要件定義（API側が求める要素）

### 最小スキーマ（1メニューあたり）

| 項目 | 必須 | 説明 |
|------|------|------|
| **条件** | ○ | 期、種目、対象（強化/育成/障害者/マスターズ等）、距離タイプ（S/M/D）、総距離、練習時間 |
| **本文** | ○ | warmUp, drill, kick, pull, preMain, main, down のテキスト（現状のJSON形式） |
| **作成意図** | ○ | 50〜200字。「強化選手向けに〇〇を狙った」「障害者クラスで〇〇に配慮」等 |
| intention / coachingPoint / caution | △ | あれば参照の質が上がる。なければ本文のみでも可 |
| total | ○ | 合計距離（整合確認用） |

### 必要枚数（データ量）の目安

| フェーズ | 枚数 | 用途 |
|----------|------|------|
| **最小** | 5〜10枚 | 文体・粒度の参照。few-shot として毎回2〜3件をプロンプトに含める |
| **推奨** | 20〜30枚 | 条件の分散（S/M/D、複数の期、強化/育成/障害者等）。類似検索の母集団 |
| **理想** | 50枚以上 | RAG（類似検索）で「今回に近い3件」を毎回選んで渡す。無限に広げる土台 |

**要点**：枚数より**条件のバラつき**と**作成意図の明記**が重要。5枚でも意図がしっかり書いてあれば価値は高い。

## 2. 高城コーチへのリクエスト内容

### 提供していただきたい形式

**A. 理想：スプレッドシート or JSON（1行＝1メニュー）**

| 期 | 種目 | 対象 | 距離タイプ | 総距離 | 練習時間 | 作成意図 |
|----|------|------|------------|--------|----------|----------|
| 3 | Fr | 強化 | S | 3000 | 90 | 発展期・ショート選手に後半の粘りをつける。Pre-Mainでスピード刺激を入れてMainに繋げた |
| 5 | Fr | 障害者 | M | 4000 | 120 | 障害特性に合わせレスト長め。フォーム崩れにくい構成 |
| ... | ... | ... | ... | ... | ... | ... |

＋ 別列または別シートで：warmUp, drill, kick, pull, preMain, main, down, intention, coachingPoint, caution

**B. 現実的：既存メニュー（PDF/手書き）＋ 1枚あたりの簡易シート**

メニュー本文はそのまま、以下の情報を**1枚につき1行**でいただく：

```
【メニュー#1】
条件: 期③、種目Fr、対象=強化、Sタイプ、3000m、90分
作成意図: 発展期ショート選手。後半の粘り。Pre-Mainでスピード刺激→Mainへ。
```

→ こちらでテキストを抽出し、条件・意図と紐付けてDB化する。

### コーチにお願いするポイント

1. **作成意図を短くでよいので必ず書く**（50〜200字目安）
   - 「誰向けで、何を狙ったか」が分かれば、APIがそれを手がかりにスタイルを合わせやすい
   - 例：「障害者クラス。動きの負荷を抑えつつ、水感を維持する狙い」

2. **対象の明示**
   - 強化 / 育成 / 障害者 / マスターズ / 初級 等、ざっくりで可

3. **形式は柔軟**
   - Excel、Googleスプレッドシート、メモ帳の箇条書き、写真＋メモ 等、いずれでも可
   - 後からエンジニア側で整理する前提でOK

## 3. 私（アンドリュー）からAIへの情報提供

### 効果が高い情報（優先度順）

| 優先度 | 内容 | 形式例 | 効果 |
|--------|------|--------|------|
| 1 | **パターン辞書**（用語と使い方） | menu-patterns.md | Des、odd/even、1H/1E Alt 等を「語彙」として使わせる |
| 2 | **条件×意図のマッピング** | 期×対象でどんなトーン・量が適切か | 「障害者＝レスト長め、フォーム優先」等を明文化 |
| 3 | **悪い例（NG例）** | 「こう書いたらダメ」の具体例 | チープ・汎用表現の排除 |
| 4 | **用語の定義** | Des＝本数ごとにタイム落とす、等 | 表記ゆれを減らす |

### パターン辞書に含めたい項目（例）

```
## セット構成
- Des / 1-4 Dec: 本数ごとにタイムを落とす
- 1H/1E Alt: 1本目Hard・2本目Easy を交互
- odd: X / even: Y: 奇数本でX、偶数本でY

## ドリル変形
- odd: ヘッドアップ / even: キャッチアップ
- odd: Drill / even: Swim
- 1本目 H-E / 2本目 E-H / 3本目 E / 4本目 H
```

これらを document 化し、プロンプトで「必ず参照して使用せよ」と指示する。

### 完成時の状態

| 要素 | 状態 |
|------|------|
| **サンプルDB** | 20〜50件。条件・本文・作成意図を紐付けて保存。必要に応じてRAGで検索 |
| **パターン辞書** | セット構成・ドリル変形を網羅。プロンプトで常時参照 |
| **思想・プロトコル** | 既存のまま。安全・期の制御・トーンを担保 |
| **類似検索** | 入力条件に近いサンプルを0〜3件取り出し、few-shot として付与 |
| **出力品質** | 「本数×距離（EN1）」ではなく、Des、odd/even、1H/1E Alt 等の具体性を持つ |

### 段階的な到達イメージ

| フェーズ | 内容 | あなたの準備 |
|----------|------|--------------|
| **Phase 1** | パターン辞書拡充、プロンプト強化 | 用語・パターンの整理（私と共同で） |
| **Phase 2** | サンプル 5〜10 件を few-shot に追加 | 高城コーチへ 5〜10 件＋意図の依頼 |
| **Phase 3** | サンプル 20〜30 件、類似検索（RAG）導入 | 高城コーチへさらに 10〜20 件の依頼 |
| **Phase 4** | 継続拡張。障害者・強化等の条件別チューニング | 対象別サンプルの追加依頼 |

## 5. まとめ：今すぐ着手できること

**高城コーチへ**  
- 「5〜10枚でよいので、過去メニュー＋条件・作成意図」の提供をお願いする  
- 形式は問わない（表・メモ・写真＋一言 等）  
- **作成意図**（誰向けで何を狙ったか）が最重要  

**あなたから**  
- パターン辞書のたたき台（Des、odd/even、1H/1E 等）の列挙  
- 「障害者向けなら〇〇」「強化向けなら〇〇」のような条件別の指針  

**エンジニア側**  
- サンプル用のスキーマ・保存場所の整備  
- パターン辞書の組み込み、プロンプトの更新  
- Phase 2 以降で類似検索（RAG）の実装  

この流れで進めれば、思想だけでは届かなかった「質」を、段階的に引き上げていける構成になっています。
