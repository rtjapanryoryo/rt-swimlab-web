# 距離乖離の根本分析と対策

**作成日**: 2026-03  
**現象**: 目標6000m指定 → 出力3600m（約60%）。8000m指定 → 3950m（約49%）。

---

## 1. 何が問題で、なぜ紐付けができないのか

### 1.1 根本原因：AIの生成順序と「典型値」への寄り

| 原因 | 説明 |
|------|------|
| **内容優先生成** | プロンプトでは「まず距離配分を決めてから内容を設計」と書いてあるが、LLMはその順序で思考しない。内容（典型メニュー）を先に生成し、距離は後から合わせる。 |
| **典型セッションへの固定** | 学習データ上の「60〜90分練習」はおおよそ3500〜4500mが多い。モデルは無意識にこの「典型的な量」へ引き寄せられる。 |
| **距離指示の希釈** | システムプロンプトが6セクション（コーチ思想、プロトコル、辞書、Web検索等）で長く、距離の最優先指示がトークン列の途中に埋もれる。 |
| **矛盾するシグナル** | 「量より質」「フォームを崩さない」などの方針が、無意識に「少なめの量」へバイアスをかける。 |
| **M フィールドの誤用** | warmUpM 等を「内容に合わせて埋める」と解釈している。正しくは「目標に合わせて内容を設計し、M はその結果」であるべき。 |

### 1.2 技術的な抜け穴

- **テンプレートの例が固定値**  
  JSON 例で `warmUpM: 720` 等を出すが、あくまで「例」であり、モデルは自ら生成した内容に合わせて別の数値を出力する。
- **リトライが同じ失敗を繰り返す**  
  temperature 0.15 でも、同じ「典型メニュー」へ戻りやすい。ヒントを増やしても、根本の制御構造が変わっていない。
- **パースと M の二重基準**  
  M を優先するが、M が不正だとパースにフォールバック。AI が「内容ベースの M」を出力すると、パースも M も両方低い値になり、結局 3600m のまま。

## 2. トリガー（何がきっかけで乖離するか）

| トリガー | 説明 | 例 |
|----------|------|-----|
| **練習時間のアンカー** | 60分・90分が「標準」と解釈され、それに合う量（3500m前後）に寄る | 60分+6000m → 約3500m |
| **期・レベルの解釈** | 基礎形成・中級を「控えめ」と解釈し、距離を下げる | ②基礎形成+中級 |
| **ブロック構成の慣性** | W-up 2〜3段階、Kick 2構成などの「形」は守るが、1段階あたりの距離が短い | 各ブロックが想定の約 60% |
| **Pre-Main と Main の優先** | 「Main をしっかり」という指示の結果、Main 以外を削って Main を目立たせる | W-up・Drill・Kick が少なめ |

## 3. 根本対策（対症療法でなく設計変更）

### 3.1 方針：距離は「AIに決めさせない」

- 距離配分は**システムが算出**し、**固定値として渡す**。
- AI の役割は「その距離を満たす内容を書くこと」に限定する。

### 3.2 実装方針

#### A. 距離の完全固定（必須）

```
【絶対ルール】以下の数値は変更禁止。そのまま JSON に出力すること。
warmUpM=720, drillM=720, kickM=720, pullM=1020, preMainM=720, mainM=2100, downM=300
合計=6000m。各ブロックのテキストは、この距離に合わせて設計すること。
「少なめでよい」は禁止。この数値に届くまでセグメントを増やすこと。
```

- プロンプト内で `alloc` を「変更禁止」として明示。
- JSON スキーマの例でも、この固定値をそのまま使う旨を書く。

#### B. 距離優先のプロンプト構成

1. **ユーザーメッセージの先頭**に、上記の距離固定ブロックを置く。
2. システムプロンプトの距離指示を**1セクションに集約**し、先頭付近に移動。
3. その他のルール（コーチ思想、プロトコルなど）は、距離の後に配置。

#### C. 2フェーズ生成（オプション・信頼性重視）

- **Phase 1**: 距離配分のみ出力。検証して合計が目標±100m なら OK。
- **Phase 2**: 検証済みの距離を前提に、各ブロックの内容を生成。

#### D. 温度とリトライ

- 初回 temperature: 0.3 に下げる。
- リトライ時: 0.1。

## 4. 練習内容の連動性

### 4.1 現状の構造

```
W-up → Drill → Kick → Pull → Rest → Pre-Main → Main → Down
```

### 4.2 連動性の問題点

| 問題 | 説明 | 対策 |
|------|------|------|
| **目的の断絶** | W-up と Drill、Kick と Pull の「狙い」が明示されず、並列の羅列になる | 各ブロックに「今日の狙いとの関係」を1行で明記させる |
| **強度のジャンプ** | Drill（低強度）から Kick（EN1）への移行が唐突 | 「Drill で感覚をつかみ、Kick で下半身を目覚めさせる」等の橋渡し表現 |
| **Pre-Main の役割不明** | 「Main の橋渡し」とあるが、内容が Main と重なりがち | Pre-Main は「Main−1 強度」「Main のリハーサル」と明示 |
| **Rest の位置** | Rest がいつ入るかが曖昧 | 「Pre-Main 後・Main 前」と固定し、プロトコルに明記 |

### 4.3 ブロック間の連動ルール（プロトコル追加案）

```
【ブロック連動】
- W-up: 今日の Main 種目・強度を見据えた「体の準備」。Cho で全身をほぐす。
- Drill: W-up で泳いだ種目（Fr/Ba/Br/Fly）の技術テーマに直結。Main で使う感覚を先取り。
- Kick: Drill の感覚をキックで支える。下半身の土台と泳ぎのリズムづくり。
- Pull: 効率（DPS）とストロークの安定。Main の泳ぎの土台。
- Pre-Main: Main より1段階下の強度で、Main のペース感・ストローク感を確認。
- Main: 今日の中心。上記全てが Main のために組み立てられていることを明示。
- Down: クールダウン。神経刺激を入れる場合は Main 直後〜Down 前。
```

### 4.4 Warm-up 500〜1000m について

- プロトコルでは W-up は「総距離の 10〜15%」。
- 6000m なら 600〜900m。500〜1000m は妥当な範囲。
- **問題は W-up が短くなりすぎること**（例: 200m×2＝400m で止まる）。  
  → 「W-up は目標 XXm。2〜3段階で、合計 XXm に必ず届ける」と数値で指定する。

## 5. 推奨アクション（優先度順）

1. **距離の完全固定**（route.ts 修正）  
   - `alloc` を「変更禁止」として強調。  
   - M フィールドは必ず `alloc` の値をそのまま出力するよう指示。

2. **プロンプト構成の見直し**  
   - 距離ブロックをユーザーメッセージの先頭に移動。  
   - システムプロンプト内で距離を最優先セクションにまとめる。

3. **temperature 調整**  
   - 初回 0.5 → 0.3。  
   - リトライ 0.15 → 0.1。

4. **ブロック連動ルールの追加**  
   - docs/RT_MENU_GENERATION_RULES_JA.md に上記「ブロック連動」を追記。  
   - CORE_SYSTEM_PROMPT またはカスタム用プロンプトに反映。

5. **2フェーズ生成の検討**  
   - 上記 1〜4 で改善しない場合に導入。  
   - Phase 1: 距離のみ。Phase 2: 距離固定で内容生成。
